 LangGraph 可以理解为：用“有状态的有向图”来编排一串可控的处理步骤（  nodes），每个节点拿到同一个 state（通常是一个 dict /
  dataclass），做增量更新，然后把更新后的 state
  传给下一个节点；图可以是线性的，也可以根据条件分支/循环，并且支持
  把每步的中间状态流式输出（便于进度条、调试、可观测性）。

  下面结合你这个 repo 讲清两部分：LangGraph 概念 +
  本项目的实现方式。
  
  ---
  1) LangGraph 的核心概念（你需要掌握的最少集合）

  1. StateGraph(StateType)
  这是图的“类型声明”：告诉 LangGraph，节点间流转的数据结构长什么样。

    - 常见是 TypedDict、Pydantic model、dataclass，或者简单
  dict（取决于版本/用法）。
    - 节点函数签名通常是：def node(state) -> state
  或返回部分更新（某些模式下）。
  2. Node（节点）
  节点就是一个纯函数/可调用对象：输入 state，输出更新后的 state。   
  节点里做 I/O（读文件、写报告）也行，但从工程角度最好“显式写回     
  state + 记录日志”。
  3. Edge（边）与 entry/finish
    - add_edge(A, B)：A 跑完就去 B（最常见线性流水线）。
    - set_entry_point("...")：起点节点
    - set_finish_point("...")：终点节点
  4. compile() & invoke()
    - compile() 把“声明的图”编译为可运行体（类似把 DAG
  变成执行器）。
    - 执行时通常调用 graph.invoke(initial_state)（或 stream 变体）。
  5. 条件分支（conditional edges）
  LangGraph 支持根据 state 的某个字段决定走哪个分支（例如异常则走   
  error handler）。你们当前这版基本是“严格顺序”的线性图。

  ---
  2) 本项目里 LangGraph 怎么实现的（落到具体文件）

  2.1 图是怎么搭起来的

  graph/builder.py
  把所有节点按固定顺序串起来：graph/builder.py:32-53

  - 用 StateGraph(CANState) 声明状态类型：graph/builder.py:33       
  - g.add_node(...) 注册 10 个节点：graph/builder.py:35-44
  - 用 NODE_ORDER 循环
  add_edge，保证严格线性顺序：graph/builder.py:47-49
  - entry 是 validate_input，finish 是
  ai_analyze：graph/builder.py:50-51
  - compile_graph() 返回可执行图：graph/builder.py:56-57

  这意味着你当前流水线是：

  validate_input → load_skills → parse_blf → decode_dbc →
  build_dataframe → anomaly_detect → summarize → report_generate →  
  signal_index → ai_analyze

  2.2 state（贯穿全流程的数据结构）

  graph/state.py 定义了 dataclass：CANState（这就是 LangGraph       
  的“单一事实来源”）

  关键字段：
  - 输入/配置：blf_path, dbc_path, config, enable_ai, output_dir    
  - 中间产物：raw_msgs, decoded_df, anomalies, diagnosis,
  anomaly_slices, signals_index, ai_report ...
  - 执行状态：status, error, logs

  它还有一个很关键的可观测性设计：
  - add_stage_event()
  记录每个节点的运行/成功/失败事件：graph/state.py:66-68
  - fail() 统一设置失败状态并追加日志：graph/state.py:69-85

  2.3 节点的写法（模式）

  以 validate_input 为例：graph/nodes/validate_input.py:9-41        

  典型模式是：
  1. 写入 “running” 事件
  2. 做校验 / 处理
  3. 失败就 return state.fail(...)（会打失败日志）
  4. 成功就追加 “success” 事件并返回 state

  注意：你们的节点是“就地修改 state 再返回 state”（dataclass        
  可变字段），这在工程上很常见。

  2.4 可选节点（AI 不影响主流程）

  graph/nodes/ai_analyze.py 做了一个很明确的设计：AI
  是可选的，不能把主流程搞挂：graph/nodes/ai_analyze.py:11-15       

  - enable_ai == False 时直接记 success 返回
  - 即使缺少输入（diagnosis/anomalies），也只是记 failed event      
  并返回 state（不调用 state.fail() 去把全局置为
  failed）：graph/nodes/ai_analyze.py:18-31

  这体现了 LangGraph 的一个工程优势：你可以把“可选能力”放在图的末端 
  ，逻辑上仍是一个节点，但运行策略更宽松。
